Lesson 13-1: テスト可能な設計

Concept

テストが書きにくい関数には、たいてい共通点があります。 「毎回結果が変わるもの」や「外の世界に触るもの」が、計算の中に混ざっているのです。

  • 現在時刻（SystemTime::now()）
  • 乱数
  • ファイル・ネットワーク・標準入出力

これらを計算から引き離して、引数として受け取るようにすると、テストは一気に書きやすくなります。

Why?

テストの基本は「この入力なら、この出力になるはず」と確かめることです。 ところが関数の中で現在時刻を読んでいると、同じ入力でも実行した時間によって結果が変わるので、 「この出力になるはず」が書けません。

Bad Example

時間帯に応じてあいさつを返す関数です。

use std::time::{SystemTime, UNIX_EPOCH};

fn greeting() -> &'static str {
    // 現在時刻から「今が何時か」を計算する（UTC）
    let secs = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .unwrap()
        .as_secs();
    let hour = (secs / 3600) % 24;

    if hour < 12 {
        "おはようございます"
    } else if hour < 18 {
        "こんにちは"
    } else {
        "こんばんは"
    }
}

fn main() {
    println!("{}", greeting());
}

Problem

この関数に対して、「朝なら『おはようございます』を返す」というテストは書けるでしょうか。

#[test]
fn morning_greeting() {
    assert_eq!(greeting(), "おはようございます"); // 朝に実行したときだけ通る
}

このテストは実行した時刻によって通ったり落ちたりします。 夜に CI が動けば落ち、朝に手元で動かせば通る——こういうテストは信用できません。 しかも「夕方の場合」をテストしたければ、夕方まで待つしかありません。

Think

問い: この関数の中で、「毎回変わる部分」と「毎回同じ計算をする部分」はどこですか？ 2つを分けるとしたら、どう分けますか？

Hint

「今が何時か」を調べる部分と、「何時なら何と言うか」を決める部分に分けてみてください。 後者は、時刻を引数でもらえば、いつ実行しても同じ結果になります。

Solution 
use std::time::{SystemTime, UNIX_EPOCH};

/// 「何時なら何と言うか」を決める。時刻を引数でもらうので、いつ実行しても結果は同じ。
fn greeting_for_hour(hour: u64) -> &'static str {
    if hour < 12 {
        "おはようございます"
    } else if hour < 18 {
        "こんにちは"
    } else {
        "こんばんは"
    }
}

/// 「今が何時か」を調べて、上の関数に渡すだけ。ここはテストしなくてよいほど薄い。
fn greeting() -> &'static str {
    let secs = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .unwrap()
        .as_secs();
    greeting_for_hour((secs / 3600) % 24)
}

fn main() {
    // どの時間帯も、好きなときに確かめられる
    assert_eq!(greeting_for_hour(8), "おはようございます");
    assert_eq!(greeting_for_hour(15), "こんにちは");
    assert_eq!(greeting_for_hour(21), "こんばんは");

    // 境目もはっきり確かめられる
    assert_eq!(greeting_for_hour(11), "おはようございます");
    assert_eq!(greeting_for_hour(12), "こんにちは");

    println!("{}", greeting());
}

大事なのは、判断のロジック（greeting_for_hour）が外の世界に触らなくなったことです。 こういう関数は「同じ入力なら必ず同じ出力」になるので、テストがとても書きやすくなります。

一方、greeting は時刻を読んで渡すだけの薄い関数になりました。 薄い部分は間違えようがないので、無理にテストしなくても大きな問題にはなりません。

もう1つのやり方: 「調べ方」を引数でもらう

時刻を1回読むだけなら、上のように値を渡せば十分です。 しかし「処理の途中で何度も時刻を読む」ような場合は、時刻の調べ方そのものを引数でもらう方法もあります。

/// now: 「今の時刻（時）を返す関数」。本番では本物の時計、テストでは固定値を渡す。
fn greeting_with<F: Fn() -> u64>(now: F) -> &'static str {
    let hour = now();
    if hour < 12 {
        "おはようございます"
    } else {
        "こんにちは以降"
    }
}

fn main() {
    // テストでは「いつも8時を返す時計」を渡せる
    assert_eq!(greeting_with(|| 8), "おはようございます");
    assert_eq!(greeting_with(|| 20), "こんにちは以降");
}

クロージャ（|| 8）は「呼ばれたら 8 を返す小さな関数」です。 本番では本物の時計を読むクロージャを、テストでは固定値を返すクロージャを渡します。 これを依存性の注入（dependency injection）と呼ぶことがありますが、 やっていることは「必要なものを中で作らず、外から渡してもらう」だけです。

Deep Dive: 「テストしにくい」は設計のサイン

テストを書こうとして次のように感じたら、設計を見直すチャンスです。

感じたことたいていの原因見直し方
「実行するたびに結果が変わる」時刻・乱数を中で読んでいる値を引数でもらう
「ファイルを用意しないとテストできない」I/O と計算が混ざっている読む部分と計算する部分を分ける（12-2 の run と count_words）
「準備が長すぎる」1つの関数が多くのことをしすぎている関数を分ける
「内部の関数を直接呼びたくなる」公開APIが大きすぎる／小さすぎる公開範囲を見直す（12-4）

これまでの演習でも、同じ形が何度も出てきました。 12-2 の count_words（計算）と run（ファイルを読む）の分離は、まさにこのLessonの考え方です。

Challenge

自分のコードで SystemTime::now()・乱数・std::fs を関数の中で直接使っている箇所を1つ探し、 「調べる部分」と「決める部分」に分けてみてください。

Review

  • テストしにくいコードの共通点（時刻・乱数・I/O が混ざっている）を説明できる
  • 「調べる部分」と「決める部分」を分けて、決める部分をテストできる
  • 値や関数を引数でもらう（依存性の注入）ことで、テストで差し替えられるようにできる
