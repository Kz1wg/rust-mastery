Lesson 15-3: FFI

Concept

FFI（Foreign Function Interface）は、他の言語で書かれた関数を呼ぶ／他の言語から Rust の関数を呼ぶための仕組みです。 ほとんどの場合、相手は C 言語（または C と同じ呼び出し規約を持つもの）です。

C の関数を呼ぶ瞬間、Rust のコンパイラは相手の中身を一切チェックできません。 だから FFI の呼び出しは、必ず unsafe になります。

Why?

既存の C ライブラリ（画像処理、暗号、OS の機能など）を使いたい場面は多くあります。 そのとき、Rust の安全性の保証が境界で途切れることを理解していないと、 安全に見える Rust コードの中にバグを持ち込むことになります。

C の関数を呼ぶ

C の標準ライブラリは、ほとんどの環境で最初からリンクされています。依存 crate なしで呼べます。

use std::ffi::{c_char, c_int, CString};

extern "C" {
    fn abs(x: c_int) -> c_int;
    fn strlen(s: *const c_char) -> usize;
}

fn main() {
    // SAFETY: C の abs は INT_MIN（i32::MIN）を渡すと未定義動作になるが、-7 はそれに当たらない。
    let a = unsafe { abs(-7) };
    assert_eq!(a, 7);

    // C の文字列は「最後に \0 が付いたバイト列」。Rust の String とは形が違う。
    let s = CString::new("hello").unwrap();
    // SAFETY: s.as_ptr() は \0 終端の有効な文字列を指しており、s はこの行の間生きている。
    let n = unsafe { strlen(s.as_ptr()) };
    assert_eq!(n, 5);
}

extern "C" { ... } は、「こういう名前と型の C の関数がある」という宣言です。 Rust はこの宣言を信じるしかありません。型を書き間違えても（例えば abs の引数を i64 と書いても）、 コンパイルは通ってしまい、実行時におかしなことが起きます。

Rust 2024 edition では、この宣言ブロックを unsafe extern "C" { ... } と書く必要があります。 「この宣言の正しさは、書いた人が保証している」ことを明示するためです。

文字列の受け渡し: 境界で形が変わる

Rust の String / &strC の文字列
終わりの印長さを別に持っている最後の \0（ヌル文字）
途中の \0含めてよい含められない（そこで終わりとみなされる）
文字コード必ず UTF-8決まっていない

この違いを吸収するのが、標準ライブラリの2つの型です。

型向き役割
CStringRust → C\0 を末尾に付けた、C に渡せる文字列を作る。途中に \0 があるとエラー
CStrC → RustC から受け取った \0 終端の文字列を読む

Bad Example: 途中に \0 を含む文字列

use std::ffi::CString;

fn main() {
    let result = CString::new("abc\0def");
    // C に渡すと "abc" までしか読まれない。黙って切れるより、エラーで止めてくれる。
    assert!(result.is_err());
}

Think

問い: 「Rust の &str を受け取り、C の strlen で長さを数える」関数を、safe な関数として公開したいとします。 呼び出し側にどんな失敗の可能性を伝える必要がありますか？（15-2 の safe abstraction の条件を思い出してください。）

Solution

途中に \0 を含む文字列は、C の文字列に変換できません。 これはユーザー入力でも起こりうる失敗なので、panic ではなく Result で返すのが適切です（13-3）。

use std::ffi::{c_char, CString, NulError};

extern "C" {
    fn strlen(s: *const c_char) -> usize;
}

/// C の strlen で文字列の長さ（バイト数）を数える。
/// 途中に \0 を含む文字列は C に渡せないので、Err を返す。
pub fn c_strlen(s: &str) -> Result<usize, NulError> {
    let c = CString::new(s)?; // ここで \0 チェックが行われる
    // SAFETY: c は \0 終端の有効な C 文字列で、この呼び出しの間 c は生きている。
    Ok(unsafe { strlen(c.as_ptr()) })
}

fn main() {
    assert_eq!(c_strlen("hello"), Ok(5));
    assert!(c_strlen("a\0b").is_err());
}

呼び出し側から見ると、c_strlen は普通の safe な関数です。 「C の文字列の作法」はすべて関数の中に閉じ込められ、失敗の可能性は Result として型に現れています。 これが、FFI における safe abstraction の典型的な形です。

よくある落とし穴: 次のように書くと、CString がその行の終わりで解放され、 strlen が解放済みのメモリを読むことになります。

let ptr = CString::new(s)?.as_ptr(); // 一時的な CString がこの行の終わりで解放される
unsafe { strlen(ptr) }               // 解放済みのメモリを指している！

生ポインタには lifetime が無いので、借用チェックはこの誤りをエラーにはできません。

rustc には、この形を見つけて警告する lint（temporary_cstring_as_ptr）があります。 ただし Rust 1.75 で試したところ、CString::new(s).unwrap().as_ptr() の形では警告が出ましたが、 上の CString::new(s)?.as_ptr() の形（? を使った形）では警告が出ませんでした。 （新しい Rust では、同種の検出が dangling_pointers_from_temporaries という lint に広がっています。）

警告に頼らず、CString は変数に束縛して、使い終わるまで生かしておく、と覚えておいてください。

見落としやすい前提: C の関数にも「渡してはいけない値」がある

C の abs は、INT_MIN（Rust の i32::MIN）を渡すと未定義動作になります。 （-i32::MIN は i32 に収まらないためです。）

つまり、abs をそのまま包んだ pub fn c_abs(x: i32) -> i32 は、safe な関数として公開してはいけません。 c_abs(i32::MIN) と呼ばれた瞬間に、safe なコードから未定義動作が起きてしまうからです（15-2 の条件に反します）。

use std::ffi::c_int;

extern "C" {
    fn abs(x: c_int) -> c_int;
}

/// C の abs を呼ぶ。i32::MIN の絶対値は i32 で表せないので None を返す。
pub fn c_abs(x: i32) -> Option<i32> {
    if x == i32::MIN {
        return None; // C に渡す前に、未定義動作になる入力を弾く
    }
    // SAFETY: x は i32::MIN ではないので、abs の未定義動作の条件に当たらない。
    Some(unsafe { abs(x) })
}

fn main() {
    assert_eq!(c_abs(-7), Some(7));
    assert_eq!(c_abs(i32::MIN), None);
}

C の関数を包むときは、その関数のドキュメント（man ページなど）で「未定義動作になる条件」を確認し、 Rust 側で先に弾くことが、safe abstraction を作る作業の中心です。 // SAFETY: コメントを書こうとして「どんな値でも安全」と書きかけたら、本当にそうか調べてください。

Rust の関数を C から呼べるようにする

逆向きに、Rust の関数を C から呼べるようにすることもできます。

/// C から add(2, 3) のように呼べる関数。
#[no_mangle]
pub extern "C" fn rust_add(a: i32, b: i32) -> i32 {
    a + b
}

fn main() {
    assert_eq!(rust_add(2, 3), 5);
}
書き方意味
extern "C"C と同じ呼び出し規約（引数の渡し方）を使う
#[no_mangle]関数名を変形せず、C から rust_add という名前で見えるようにする

Rust 2024 edition では #[unsafe(no_mangle)] と書きます。同じ名前の関数が他にあると衝突するため、 「名前の一意性は書いた人が保証する」という意味で unsafe が付きました。

C 側に渡す関数では、panic を境界の外に漏らさないことにも注意してください。 C は Rust の panic を扱えません。panic しうる処理は std::panic::catch_unwind で受け止めるか、 エラーコードを返す設計にします。
