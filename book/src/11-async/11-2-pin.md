# Lesson 11-2: `Pin` / `Unpin`

## Concept

11-1 で見たとおり、`async fn` は状態機械に変換され、`.await` をまたぐ変数はその中に保存されます。
ここで問題が起きます。**状態機械が、自分の中の変数への参照を持つ**ことがあるのです。

```rust,ignore
async fn example() {
    let data = String::from("hello");
    let slice = &data[..];   // data への参照
    something().await;       // ここで状態機械に保存される
    println!("{slice}");     // 再開後に使う
}
```

`data` と `slice`（`data` を指す参照）が、**同じ構造体の中に同居**します。08-2 の Deep Dive で
「自己参照構造体は作れない」と書いたものが、コンパイラによって作られるわけです。
もしこの構造体がメモリ上で**移動**したら、`slice` は古い場所を指したままになります。

`Pin` は、「この値はもう動かさない」と約束するための道具です。

## Why?

`Pin` は async を使うときに必ず目にしますが、「なぜ必要か」を知らないと、
`Box::pin` を呪文のように使うことになります。

## `Unpin`: 動いても困らない型

ほとんどの型は、移動しても困りません（自分への参照を持たないため）。
そういう型には `Unpin` が**自動的に**実装されます。`u32`、`String`、`Vec<T>` はすべて `Unpin` です。

一方、`async` ブロックが作る `Future` は `Unpin` では**ありません**。

```rust,compile_fail,E0277
fn assert_unpin<T: Unpin>(_: T) {}

fn main() {
    let f = async { 1 };
    assert_unpin(f); // async ブロックの Future は動かせない
}
```

## Think

> **問い**: `Future::poll` のシグネチャが `fn poll(self: Pin<&mut Self>, ...)` であって、
> `fn poll(&mut self, ...)` ではないのはなぜでしょうか。

<details>
<summary>Solution</summary>

`&mut self` を渡すと、受け取った側は `std::mem::swap` や `std::mem::replace` で
**中身を丸ごと入れ替える**ことができてしまいます。それは「移動」と同じで、自己参照が壊れます。

`Pin<&mut Self>` は、「この参照からは中身を取り出したり入れ替えたりできない」という制約付きの参照です
（`Unpin` な型は例外で、`get_mut` で普通の `&mut` を取り出せます——動いても困らないからです）。

つまり `Pin` は、**`Future` の実装者に「自己参照しても安全」を保証するための型**です。
ランタイム（`poll` を呼ぶ側）には「`poll` する前に固定せよ」という義務が生まれます。

</details>

## 固定する方法

```rust
use std::future::Future;

fn main() {
    // (1) ヒープに置いて固定する。最も簡単で、どこにでも持ち運べる
    let mut boxed = Box::pin(async { 1 + 1 });

    // (2) スタック上で固定する（標準マクロ）
    let stack = async { 2 + 2 };
    let mut stack = std::pin::pin!(stack);

    // 固定した後は、Pin<&mut F> として poll できる
    let _: std::pin::Pin<&mut _> = boxed.as_mut();
    let _: std::pin::Pin<&mut _> = stack.as_mut();

    fn takes_future<F: Future>(_f: F) {}
    takes_future(async { 3 });
}
```

| 方法 | コスト | 使いどころ |
| --- | --- | --- |
| `Box::pin` | ヒープ確保1回 | `Future` を構造体に保存する、`Vec` に入れる、関数から返す |
| `std::pin::pin!` | ゼロ（スタック上） | その場で `poll` して使い切る |

11-1 の `block_on` が `Box::pin` を使っていたのは、受け取った `Future` を固定してから `poll` するためです。

## Deep Dive: 自分で `Future` を実装するときの現実

`Pin<&mut Self>` から各フィールドへ安全にアクセスすること（pin projection）は、
手で書くと `unsafe` が必要になります。そのため実務では次のどちらかを選びます。

1. **フィールドを `Box::pin` で持つ**（`Pin<Box<F>>` は `Unpin` なので、構造体全体が `Unpin` になる）
2. **`pin-project` / `pin-project-lite` crate を使う**（マクロが安全な projection を生成する）

この教材の演習では、依存を増やさないため 1 を使います。
`Pin<Box<F>>` を持つ構造体は `Unpin` になるので、`self.get_mut()` で普通に中身を触れます——
ヒープ確保の代わりに、`unsafe` を書かずに済みます。
