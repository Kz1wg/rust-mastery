# Lesson 13-1: テスト可能な設計

## Concept

テストが書きにくい関数には、たいてい共通点があります。
**「毎回結果が変わるもの」や「外の世界に触るもの」が、計算の中に混ざっている**のです。

- 現在時刻（`SystemTime::now()`）
- 乱数
- ファイル・ネットワーク・標準入出力

これらを計算から**引き離して、引数として受け取る**ようにすると、テストは一気に書きやすくなります。

## Why?

テストの基本は「この入力なら、この出力になるはず」と確かめることです。
ところが関数の中で現在時刻を読んでいると、**同じ入力でも実行した時間によって結果が変わる**ので、
「この出力になるはず」が書けません。

## Bad Example

時間帯に応じてあいさつを返す関数です。

```rust
use std::time::{SystemTime, UNIX_EPOCH};

fn greeting() -> &'static str {
    // 現在時刻から「今が何時か」を計算する（UTC）
    let secs = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .unwrap()
        .as_secs();
    let hour = (secs / 3600) % 24;

    if hour < 12 {
        "おはようございます"
    } else if hour < 18 {
        "こんにちは"
    } else {
        "こんばんは"
    }
}

fn main() {
    println!("{}", greeting());
}
```

## Problem

この関数に対して、「朝なら『おはようございます』を返す」というテストは書けるでしょうか。

```rust,ignore
#[test]
fn morning_greeting() {
    assert_eq!(greeting(), "おはようございます"); // 朝に実行したときだけ通る
}
```

このテストは**実行した時刻によって通ったり落ちたりします**。
夜に CI が動けば落ち、朝に手元で動かせば通る——こういうテストは信用できません。
しかも「夕方の場合」をテストしたければ、夕方まで待つしかありません。

## Think

> **問い**: この関数の中で、「毎回変わる部分」と「毎回同じ計算をする部分」はどこですか？
> 2つを分けるとしたら、どう分けますか？

<details>
<summary>Hint</summary>

「今が何時か」を**調べる**部分と、「何時なら何と言うか」を**決める**部分に分けてみてください。
後者は、時刻を引数でもらえば、いつ実行しても同じ結果になります。

</details>

<details>
<summary>Solution</summary>

```rust
use std::time::{SystemTime, UNIX_EPOCH};

/// 「何時なら何と言うか」を決める。時刻を引数でもらうので、いつ実行しても結果は同じ。
fn greeting_for_hour(hour: u64) -> &'static str {
    if hour < 12 {
        "おはようございます"
    } else if hour < 18 {
        "こんにちは"
    } else {
        "こんばんは"
    }
}

/// 「今が何時か」を調べて、上の関数に渡すだけ。ここはテストしなくてよいほど薄い。
fn greeting() -> &'static str {
    let secs = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .unwrap()
        .as_secs();
    greeting_for_hour((secs / 3600) % 24)
}

fn main() {
    // どの時間帯も、好きなときに確かめられる
    assert_eq!(greeting_for_hour(8), "おはようございます");
    assert_eq!(greeting_for_hour(15), "こんにちは");
    assert_eq!(greeting_for_hour(21), "こんばんは");

    // 境目もはっきり確かめられる
    assert_eq!(greeting_for_hour(11), "おはようございます");
    assert_eq!(greeting_for_hour(12), "こんにちは");

    println!("{}", greeting());
}
```

大事なのは、**判断のロジック（`greeting_for_hour`）が外の世界に触らなくなった**ことです。
こういう関数は「同じ入力なら必ず同じ出力」になるので、テストがとても書きやすくなります。

一方、`greeting` は時刻を読んで渡すだけの**薄い**関数になりました。
薄い部分は間違えようがないので、無理にテストしなくても大きな問題にはなりません。

</details>

## もう1つのやり方: 「調べ方」を引数でもらう

時刻を1回読むだけなら、上のように値を渡せば十分です。
しかし「処理の途中で何度も時刻を読む」ような場合は、**時刻の調べ方そのもの**を引数でもらう方法もあります。

```rust
/// now: 「今の時刻（時）を返す関数」。本番では本物の時計、テストでは固定値を渡す。
fn greeting_with<F: Fn() -> u64>(now: F) -> &'static str {
    let hour = now();
    if hour < 12 {
        "おはようございます"
    } else {
        "こんにちは以降"
    }
}

fn main() {
    // テストでは「いつも8時を返す時計」を渡せる
    assert_eq!(greeting_with(|| 8), "おはようございます");
    assert_eq!(greeting_with(|| 20), "こんにちは以降");
}
```

クロージャ（`|| 8`）は「呼ばれたら 8 を返す小さな関数」です。
本番では本物の時計を読むクロージャを、テストでは固定値を返すクロージャを渡します。
これを**依存性の注入**（dependency injection）と呼ぶことがありますが、
やっていることは「必要なものを中で作らず、外から渡してもらう」だけです。

## Deep Dive: 「テストしにくい」は設計のサイン

テストを書こうとして次のように感じたら、設計を見直すチャンスです。

| 感じたこと | たいていの原因 | 見直し方 |
| --- | --- | --- |
| 「実行するたびに結果が変わる」 | 時刻・乱数を中で読んでいる | 値を引数でもらう |
| 「ファイルを用意しないとテストできない」 | I/O と計算が混ざっている | 読む部分と計算する部分を分ける（12-2 の `run` と `count_words`） |
| 「準備が長すぎる」 | 1つの関数が多くのことをしすぎている | 関数を分ける |
| 「内部の関数を直接呼びたくなる」 | 公開APIが大きすぎる／小さすぎる | 公開範囲を見直す（12-4） |

これまでの演習でも、同じ形が何度も出てきました。
12-2 の `count_words`（計算）と `run`（ファイルを読む）の分離は、まさにこのLessonの考え方です。

## Exercise

**`ex050_testable_design`** — `cargo test -p ex050_testable_design` で判定します。

| 関数 | 仕様 |
| --- | --- |
| `greeting_for_hour(hour)` | 時刻（時）を受け取り、あいさつを返す。外の世界に触らない |
| `is_business_hours(hour)` | 9時以上18時未満なら `true` |
| `pick_with(items, choose)` | 「何番目を選ぶか」を決める関数 `choose` を引数でもらい、その要素を返す（乱数を外から渡す練習） |

テストは、時刻や乱数に頼らず、**いつ実行しても同じ結果になる**ことを確かめています。

「調べる部分」と「決める部分」に分けてみてください。
