# P3: ログ解析

## 何を作るか

アプリケーションのログを読み、レベルごとの件数や、エラーの多いモジュールを集計するライブラリです。

```text
2026-09-22T10:00:00 INFO [auth] login
2026-09-22T10:00:01 ERROR [db] timeout
2026-09-22T10:00:02 ERROR [db] refused
this line is broken
2026-09-22T10:00:03 ERROR [auth] bad token
```

```text
解析できた行: 4   エラー率: 75%
ERROR の多いモジュール: db 2件, auth 1件
解析できなかった行: 4行目（知らないレベル: line）
```

1行の形式は `<日時> <レベル> [<モジュール>] <メッセージ>` です。

| 章 | このプロジェクトでの使いどころ |

## 設計の問い

> **問い1**: 壊れた行が1行あったとき、そこで処理を止めるべきでしょうか。それとも続けるべきでしょうか。

<details>
<summary>考え方の例</summary>

P2（CSV）では、`CsvReader` が壊れた行に対して `Err` を返し、どうするかは呼び出し側に任せました。
このプロジェクトでは、**止めずに集計を続け、壊れた行は理由と共に記録する**設計にしています。

理由は用途の違いです。ログは、途中で書き込みが途切れた行や、別の形式が混ざった行が含まれるのが普通です。
1行壊れているだけで集計全体が止まると、ツールとして役に立ちません。

ただし、**ファイルそのものが読めない**（`io::Error`）場合は、集計を続けても意味がないので打ち切ります。
「1行の中身の問題」と「読み込みそのものの問題」で、扱いを分けているわけです。

</details>

> **問い2**: `Level` の定義の順番（Debug, Info, Warn, Error）には意味があります。どんな意味でしょうか。

<details>
<summary>考え方の例</summary>

`#[derive(PartialOrd, Ord)]` を付けた enum は、**定義した順番**で大小が決まります。
重要度の低い順に並べておくと、`Level::Warn < Level::Error` のように比べられ、
「WARN 以上だけを表示する」といった処理が `if entry.level >= Level::Warn` で書けます。

また `BTreeMap<Level, usize>` のキーにすると、集計結果がレベルの順に並びます。
derive の振る舞いを知っていると、定義の順番そのものが設計の一部になります。

</details>

> **問い3**: 「将来 JSON 形式のログにも対応するかもしれない」と考えて、`trait LogParser` を作り、
> 今の形式を `impl LogParser for TextParser` にしたくなったとします。どう判断しますか？

<details>
<summary>考え方の例</summary>

Lesson 04-1 の基準を思い出してください。**今、実装が1つしかない**なら、trait はまだ要りません。
「将来のため」は、今 trait を作る理由になりません。

JSON 形式が本当に必要になったときに、`parse_line` を trait のメソッドへ昇格させるのは難しくありません。
そのときには「2つの形式で何が共通で、何が違うか」が実物で分かるので、trait の設計も的確になります。
今の段階で想像だけで trait を作ると、実際の JSON 対応のときに合わない形になっていることがよくあります。

</details>

## 進め方

1. **`Level::from_str`**: 4つの文字列を `match` で変換する
2. **`parse_line`**: ドキュメントの手順どおりに。`splitn(3, ' ')`、`strip_prefix('[')`、`split_once(']')` が使える
3. **`summarize`**: `parse_line` の結果で分けて数える（並べ替えは用意済み）
4. **`error_rate`**: 0 で割らないように注意
