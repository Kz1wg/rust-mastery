# 18-1 Requirements: 何を作るか、何を作らないか

## この段階でやること

作るものを、**確かめられる文**で書き出します。
「使いやすい図書室アプリ」は確かめられません。
「貸出中の本は、他の人が借りられない」は確かめられます。18-7 で、そのままテストになります。

## 入力と出力

| 受け取るもの | 書くもの |
| --- | --- |
| 題材（例題なら「図書室の貸出管理」の数行の説明） | 目的 / 機能の要件（番号つき）/ 範囲外のこと / 言葉の定義 / 決めたこと |

## 考える問い

1. **誰が、何のために使うか**。一言で書けますか？
2. 要件を「〜できる」「〜のときは〜できない」の形で書けますか？ **番号**をつけてください（R1, R2 …）
3. **作らないもの**は何ですか？ 書いておかないと、作業の途中で「ついでに」が増えていきます
4. 同じ言葉を、違う意味で使っていませんか？（「期限」は返却期限？ 貸出期間？）
5. **境目**はどうなりますか？（期限の当日は延滞？ 上限ちょうどは借りられる？）
6. **ありえない入力**が来たらどうしますか？（存在しない本、返却日が貸出日より前）

問い5と6は、とくに大切です。
ここで決めなかったことは、実装するときに**その場の気分で**決まってしまいます。
そして、その決定はどこにも記録されません。

## 例題の設計メモ

> 自分で書いてから開いてください。題材の説明はこれだけです:
> **「小さな図書室で、本の貸し出しと返却を管理したい。延滞している人がわかるようにしたい。」**

<details>
<summary>例題の設計メモ（Requirements）</summary>

### 目的

図書室の係の人が、コマンドラインで本の貸出・返却を記録し、延滞を確かめられるようにする。

### 機能の要件

| 番号 | 要件 |
| --- | --- |
| R1 | 本を ID と書名で登録できる。同じ ID の本は登録できない |
| R2 | 利用者を ID と名前で登録できる。同じ ID の利用者は登録できない |
| R3 | 貸出中でない本を借りられる。返却期限は、貸出日の **14 日後** |
| R4 | 貸出中の本は、誰も借りられない |
| R5 | 1人が同時に借りられるのは **3 冊**まで |
| R6 | 延滞している本がある人は、新しく借りられない（延滞している本を返せば、また借りられる） |
| R7 | 本を返却できる。何日遅れたかがわかる。貸出中でない本は返却できない |
| R8 | 延滞している本の一覧を見られる |
| R9 | データはファイルに保存され、次に起動したときに読み戻される。ファイルが壊れていたら、何行目かを示して止まる |
| R10 | 間違った入力（存在しない ID、正しくない日付など）には、**何も変えずに**理由を伝える |

### 範囲外（作らないもの）

| 作らないもの | 理由 |
| --- | --- |
| 予約・取り置き | 本の状態が増え、最初の版としては大きすぎる（次の版の候補） |
| 延滞金 | お金を扱うと、端数や支払いの記録など考えることが一気に増える |
| 同じ本が複数冊あること | 「本」は1冊ずつの資料として扱う。同じ書名でも ID が違えば別の本 |
| 本や利用者の削除・変更 | 最初の版では登録だけ |
| 検索 | 一覧を見れば足りる規模を想定 |
| 複数人が同時に操作すること | 係の人が1人で使う前提。ファイルの同時書き込みは考えない |
| タイムゾーン | 日付だけを扱う。システムの日付は UTC で読む（`--today` で指定もできる） |

### 言葉の定義

| 言葉 | 意味 |
| --- | --- |
| 貸出日 | 本を借りた日 |
| 返却期限 | この日までに返せば遅れではない日。貸出日 + 14 日 |
| 延滞 | 今日が返却期限より**後**であること。期限の当日は延滞ではない |
| 延滞日数 | 今日 − 返却期限（延滞していなければ 0） |

### 決めたこと（境目とありえない入力）

- 期限の当日に返したら、遅れは 0 日（延滞ではない）
- 3 冊借りている人は、4 冊目を借りられない（「3 冊まで」は 3 冊を含む）
- 返却日が貸出日より前なら、エラーにする（日付の入力ミスと考える）
- ルールで断られたときは、データを**一切変えない**（途中まで変えて止まる、ということがない）

</details>

## よくある失敗

| 失敗 | 何が困るか | 直し方 |
| --- | --- | --- |
| 要件が「〜を管理する」 | 何ができれば完成なのか分からない。テストが書けない | 「〜できる」「〜のときは〜できない」に分解する |
| 範囲外を書かない | 実装中に「予約も要るのでは」と考え始め、終わらなくなる | 作らないものと、その理由を先に書く |
| 境目を決めない | 実装者（自分）がその場で決め、テストもされない | 「ちょうど」「当日」「0 個」の場合を書き出す |
| 画面やコマンドの形から書き始める | 表面の形に引きずられて、ルールを考えるのが後回しになる | コマンドの形は 18-6 で決める。ここではルールを書く |

## AI にレビューしてもらう

````text
次の設計メモは、Rust で作る小さなコマンドラインツールの要件です。
次の観点でレビューしてください。指摘は箇条書きで、それぞれに理由をつけてください。

1. テストで確かめられない、あいまいな要件はありますか
2. 境目（ちょうど、当日、0 件など）で、決めていない所はありますか
3. 要件どうしで矛盾している所はありますか
4. 範囲外にしたもののうち、無いと使い物にならないものはありますか

新しい機能の追加を提案するのではなく、書かれた範囲の中での問題を探してください。

---
（ここに設計メモを貼る）
````

最後の一文は大切です。これが無いと、AI は「予約機能もあると便利です」のような、範囲を広げる提案をしがちです。
