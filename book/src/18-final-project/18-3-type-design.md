# 18-3 Type Design: ルールを型で表す

## この段階でやること

18-2 のドメインモデルを、Rust の型に置き換えます。
目標は、**ルールの一部を、コンパイラに守らせる**ことです。

全てのルールを型で表せるわけではありません。
「3冊まで」は、実行してみないと分からないので、関数の中で確かめます。
一方、「貸出中でない本には、借りた人がいない」は、型の形で表せます。
**どのルールを型に任せ、どのルールを関数で確かめるか**を分けるのが、この段階の仕事です。

中身（関数の本体）はまだ書きません。型の定義と、関数のシグネチャだけをスケッチします。

## 入力と出力

| 受け取るもの | 書くもの |
| --- | --- |
| 18-2 の登場するもの・状態・ルール | 型の定義のスケッチ / それぞれの型を選んだ理由 / 型で表したルールと、関数で確かめるルールの分担表 |

## 考える問い

1. ID を `String` のままにすると、どんな間違いが起こりえますか？
2. 状態の図を、そのまま `enum` にできますか？ 状態ごとに持つ情報は、どの variant に入りますか？（Lesson 03-1）
3. 日付は何の型で持ちますか？ `String`？ 数？ 自分で型を作る？ crate を使う？
4. **newtype にしないもの**はどれですか？ その理由は？
5. 「全ての本」は、どんなコレクションに入れますか？（`Vec`？ `HashMap`？ `BTreeMap`？）
6. フィールドを `pub` にするか、しないか。`pub` にしないなら、何を守りたいのですか？

## ID を取り違える

問い1について、実際に試してみましょう。ID を newtype にしておくと、取り違えはコンパイルエラーになります。

```rust,compile_fail,E0308
struct BookId(String);
struct MemberId(String);

fn borrow(member: &MemberId, book: &BookId) {
    let _ = (member, book);
}

fn main() {
    let member = MemberId("M1".to_string());
    let book = BookId("B1".to_string());
    borrow(&book, &member); // 順番を間違えた
}
```

両方が `&str` なら、このコードはコンパイルが通り、「B1 という利用者は登録されていません」という、
原因の分かりにくいエラーが**実行時に**出ます（Lesson 02-2）。

### 型のスケッチ

```rust,ignore
pub struct BookId(String);        // 英数字とハイフンの 1〜16 文字（new で確かめる）
pub struct MemberId(String);      // 同上

pub struct Date { days: i32 }     // 1970-01-01 からの日数。YYYY-MM-DD と変換できる

pub struct Loan {
    pub member: MemberId,
    pub since: Date,
    pub due: Date,
}

pub enum BookState {
    Available,
    OnLoan(Loan),                 // 借りた人・期限は、貸出中のときにだけある
}

pub struct Book {
    pub id: BookId,
    pub title: String,
    pub state: BookState,
}

pub struct Member {
    pub id: MemberId,
    pub name: String,
}

pub struct Library {
    books: BTreeMap<BookId, Book>,        // 非公開
    members: BTreeMap<MemberId, Member>,  // 非公開
}

impl Library {
    pub fn borrow(&mut self, member: &MemberId, book: &BookId, today: Date) -> Result<Date, LendingError>;
    pub fn return_book(&mut self, book: &BookId, today: Date) -> Result<ReturnReceipt, LendingError>;
    // …
}
```

### ルールの分担

| ルール | 型で表す / 関数で確かめる | どうやって |
| --- | --- | --- |
| 貸出可の本には、借りた人も期限もない | **型** | `BookState::Available` は何も持たない |
| 本の ID と利用者の ID を取り違えない | **型** | 別々の newtype |
| ID は英数字とハイフンの 1〜16 文字 | **型**（作るときに1回だけ確かめる） | `BookId::new` が `Result` を返す（Lesson 02-3） |
| 日付は実在する日（2月30日はない） | **型** | `Date` は `from_ymd` / `parse` でしか作れない |
| ルールを破る変更をさせない | **型**（可視性） | `Library` のフィールドは非公開。変更は `borrow` などのメソッドからだけ |
| 同時に 3 冊まで、延滞していたら借りられない | 関数 | `Library::borrow` の中で確かめる |
| ID の重複 | 関数 | `add_book` / `add_member` の中で確かめる |

### 選んだ理由と、選ばなかった案

**ID を2つの newtype にした。** 取り違えをコンパイラが止める（上の例）。
2つの型は、規則も実装もまったく同じです。書き方の候補は3つありました。

| 書き方 | 良い点 | 困る点 |
| --- | --- | --- |
| 2つの struct を手で書く | 一番読みやすい | 同じ impl（`new` / `Display` / `FromStr`）を2回書く |
| `macro_rules!` で2つ作る（**選んだ**） | 同じ規則を1か所に書ける | マクロを読める必要がある |
| `Id<T>` と `PhantomData<T>`（Lesson 09-1） | 型が何個に増えても定義は1つ | `#[derive]` が `T` にも `Clone` などを要求するので、impl を手で書くことになる。エラーメッセージに `Id<BookTag>` のような型が出て読みにくい |

型が2つなので、マクロで十分と判断しました（Lesson 14-1「同じ impl を型ごとに並べる」）。
3つ以上に増えるなら、`Id<T>` も検討します。

**本の状態を `enum BookState` にした。** 実は `loan: Option<Loan>` でも、ありえない状態は作れません。

| 書き方 | 良い点 | 困る点 |
| --- | --- | --- |
| `loan: Option<Loan>` | 短い。`Option` のメソッドがそのまま使える | 「`None` ＝ 貸出可」という意味は、読む人が補う必要がある。状態が3つ以上になると表せない |
| `enum BookState { Available, OnLoan(Loan) }`（**選んだ**） | 状態に名前がつく。予約（取り置き）などの状態を足せる | 少し長い |

範囲外にした「予約」を、将来足す可能性があるので、`enum` にしました。

**日付を自分で作った `Date` 型にした。**

| 候補 | 判断 |
| --- | --- |
| `String`（"2026-09-25"） | 比較・n 日後の計算ができない。「2026-9-25」のような揺れも入る。選ばない |
| `u32`（通算日数） | 計算はできるが、表示するときに年月日に戻せない。`BookId` と同じく、ただの数と取り違えうる |
| `chrono` などの crate | 実務なら第一候補。ただし、この題材で必要なのは「比較」「n 日後」「差」「文字列との変換」だけ |
| 自分で `Date` を作る（**選んだ**） | 必要な機能だけを約 100 行で。依存を増やさない |

自分で作る場合は、うるう年や月末の扱いを間違えやすいので、テストを厚くします（18-7）。
時刻やタイムゾーンが必要になったら、迷わず crate に切り替えます。

**書名・名前は `String` のままにした。** 書名には「空でない」くらいしかルールがなく、
それを型にしても守れるものが少ないためです。**newtype は、守りたいルールがあるときに作ります。**

**本の集まりを `BTreeMap<BookId, Book>` にした。**

| 候補 | ID で探す | 一覧の順番 |
| --- | --- | --- |
| `Vec<Book>` | 先頭から探す | 登録順 |
| `HashMap<BookId, Book>` | 速い | **毎回変わりうる**（一覧の表示や保存ファイルの中身が、実行のたびに並び替わる） |
| `BTreeMap<BookId, Book>`（**選んだ**） | 速い | ID 順で安定 |

保存したファイルを見比べたとき（git の差分など）、順番が毎回変わると困るので、`BTreeMap` にしました。

**`Book` と `Member` のフィールドは `pub` にした。** `Library` からは `&Book`（読むだけの参照）でしか渡さないので、
利用者が書き換えることはできません。一方、`Library` のフィールドは非公開です。
公開すると、`borrow` を通さずに本の状態を書き換えられ、R5・R6 のルールを素通りできてしまいます。

</details>

## よくある失敗

| 失敗 | 何が困るか | 直し方 |
| --- | --- | --- |
| 全てを newtype にする | 守るものがない型が増え、変換のコードだけが増える | 「この型は何を守るのか」を1文で言えないなら、作らない |
| 状態を `bool` と `Option` の組み合わせで持つ | ありえない組み合わせが作れる | 状態ごとの `enum` にする |
| 複数のものにまたがるルールを、型だけで表そうとする | 型が複雑になりすぎる（typestate の乱用） | 型で表すのは「1つの値の中で完結するルール」まで。またがるルールは関数で |
| `HashMap` を選んで、出力の順番が不安定になる | テストの期待値が書けない。保存ファイルの差分が読めない | 順番に意味があるなら `BTreeMap` か `Vec` |
