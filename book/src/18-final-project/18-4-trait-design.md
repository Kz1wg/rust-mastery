# 18-4 Trait Design: trait が必要な場所はあるか

## この段階でやること

自分で trait を作る場所があるかを考えます。
そして、標準ライブラリの trait（`Display`、`FromStr` など）のうち、どれを実装するかを決めます。

先に言っておくと、**例題では自分の trait を1つも作りませんでした**。
それは手抜きではなく、候補を1つずつ検討した結果です。
Lesson 04-1 の問い「trait は共通化のためではない。では何のためか」を、実際の設計で確かめる段階です。

## 入力と出力

| 受け取るもの | 書くもの |
| --- | --- |
| 18-3 の型のスケッチ | trait の候補と、作る / 作らないの判断と理由 / 実装する標準 trait の一覧と、その理由 |

## 考える問い

1. 同じ役割で、**実装が2つ以上**あるものはありますか？（本物と、テスト用の偽物も「2つ」に数えます）
2. テストで**差し替えたい**ものはありますか？ それは、遅いもの・毎回結果が変わるもの・外の世界に触るものですか？
3. 種類が**あとから増える**ものはありますか？ 増やすのは自分ですか、利用者ですか？（Lesson 04-2）
4. trait を作らずに、**値として渡す**ことで済ませられませんか？
5. 標準の trait のうち、実装すると使う側が楽になるものはどれですか？

### 自分の trait の候補

| 候補 | 何のため | 判断 | 理由 |
| --- | --- | --- | --- |
| `Clock`（今日の日付を返す） | テストで日付を自由に決めたい | **作らない** | 日付を `today: Date` という**引数**で受け取れば足りる。時計を読むのは `main.rs` の1か所だけにする |
| `Storage`（保存と読み込み） | ファイルの代わりにメモリに保存して、テストしたい | **作らない** | 保存は「`Library` ⇔ 文字列」の変換（`store::save` / `store::load`）と、ファイルの読み書きに分けた。変換は文字列だけでテストでき、ルールのテストは `Library` を直接使えばよい。差し替える相手がいない |
| `Command`（`execute` を持つ trait、コマンドごとに struct） | コマンドを増やしやすくしたい | **作らない** | コマンドの種類は自分で決める閉じた集まり。`enum Command` と `match` なら、足し忘れがコンパイルエラーになる（Lesson 04-2） |
| `Rule`（貸出のルールを1つずつオブジェクトにする） | ルールを足し外ししやすくしたい | **作らない** | ルールは5つほどで、確かめる**順番**にも意味がある（存在しない利用者の上限を数えても意味がない）。1つの関数に上から並べたほうが読みやすい |

P5（キャッシュ）では、`Clock` trait を作りました。今回との違いは次のとおりです。

| | P5 のキャッシュ | 例題の図書室 |
| --- | --- | --- |
| 時刻を使う場所 | `get` のたびに、キャッシュの中で「今」を知る必要がある | 操作のたびに、呼ぶ側が「今日」を渡せば済む |
| 呼ぶ側に時刻を渡させると | 全ての `get` 呼び出しに時刻の引数が増え、使いにくい | コマンド1回に日付1つ。自然 |
| 結論 | trait で注入する | 引数で渡す |

「外から渡す」（Lesson 13-1）という考え方は同じで、**渡し方**が違うだけです。
値で渡せるなら、それが一番単純です。

### 実装する標準 trait

| trait | 実装する型 | 理由 |
| --- | --- | --- |
| `FromStr` | `BookId`, `MemberId`, `Date` | コマンドライン引数と保存ファイルの両方で「文字列から作る」。同じ trait なので、`fn field<T: FromStr>(…)` のように1つの generic な関数で読める |
| `Display` | 上と同じ + エラー型 | 表示と保存に使う。`FromStr` と対になるので、書き出して読み戻せる |
| `std::error::Error` | 全てのエラー型 | `?` で `Box<dyn Error>` に変換できるように（Lesson 06-2） |
| `Ord`, `Hash` | `BookId`, `MemberId`, `Date` | ID は `BTreeMap` のキーに、日付は比較（期限を過ぎたか）に使う |
| `Clone`, `PartialEq`, `Debug` | ほぼ全ての型 | テストで `assert_eq!` を使うため。`Library` の `Clone` は「断られたら何も変わらない」ことを確かめるテストでも使う |
| `Copy` | `Date` | 小さな値なので、コピーで受け渡したほうが自然（`&Date` を書かずに済む） |
| `Default` | `Library` | 空の図書室を `Library::default()` で作れる |

`Copy` は `BookId` には付けません。中に `String` を持っているので、付けられません。
付けられる型でも、**あとで外すと利用者のコードが壊れる**ので、付けるのは「小さく、今後も小さい」と言える型だけにします（Lesson 04-4）。

### trait を作ることになる場面（将来のメモ）

- 保存先が2つになったとき（ファイルと SQLite を選べる、など）→ `Storage` trait を検討する
- 外部の API（書誌情報の取得など）に問い合わせるようになったとき → テストで偽物に差し替えるための trait を作る（P4 と同じ理由）

## よくある失敗

| 失敗 | 何が困るか | 直し方 |
| --- | --- | --- |
| 「あとで差し替えられるように」と、実装が1つしかない trait を作る | generic や `dyn` が広がり、読みにくくなる。差し替える日は来ないことが多い | 2つ目の実装が**実際に必要になったとき**に作る（Lesson 04-5） |
| 閉じた種類の集まりを trait + struct で作る | 種類を足し忘れても気づけない。`match` による網羅の確認が効かない | 自分で種類を決めるなら `enum` |
| テストのためだけに、全てを trait にする | 本物のコードの構造がテストの都合で決まる | まず「値で渡す」「純粋な関数に分ける」を試す |
| 標準 trait を実装しない | `to_string()` や `parse()` が使えず、同じ変換関数を何度も書く | 表示・変換・比較に使うなら、標準 trait で |
