# 18-5 Error Design: 失敗の種類と、誰がそれを処理するか

## この段階でやること

プログラムが失敗する場面を全て書き出し、次の3つを決めます。

- 失敗を**どの型**で表すか
- その失敗を**誰が処理するか**（その場で回復する？ 呼んだ側に返す？ 利用者に見せて終わる？）
- 利用者に**何を伝えるか**

Chapter 06 で学んだ「library と application のエラー設計の違い」（Lesson 06-4）を、
1つのプログラムの中で両方使う段階です。
例題のツールは、ルールを守らせる部分（library 的）と、コマンドとして動く部分（application 的）の両方を持っているからです。

## 入力と出力

| 受け取るもの | 書くもの |
| --- | --- |
| 18-1 の要件（とくに R9・R10）、18-3 の型 | 失敗の一覧 / エラー型の設計 / 誰が処理するか / 終了コード / panic してよい場所 |

## 考える問い

1. 失敗する場面を、**原因の種類**で分けてください。利用者の操作ミス？ 入力の形の誤り？ ファイルの問題？ プログラムのバグ？
2. 失敗の種類によって、**呼んだ側の対応は変わりますか**？ 変わるなら、型で区別する必要があります
3. 1つの enum にまとめるか、操作ごとに分けるか。何を基準に決めますか？
4. 利用者がエラーメッセージを見たとき、**どこを直せばよいか**分かりますか？（何行目？ どの ID？）
5. 失敗したとき、データが**途中まで変わった状態**で残ることはありませんか？（R10）
6. `panic!`（`unwrap` / `expect` を含む）してよいのは、どんな場面ですか？

### 失敗の一覧と、表す型

| 原因の種類 | 例 | 型 | 作られる場所 |
| --- | --- | --- | --- |
| 値の形の誤り | `B 001`（空白）、`2026-02-30` | `InvalidId` / `ParseDateError` | 各型の `new` / `parse` |
| ルールによる拒否 | 貸出中、上限、延滞、存在しない ID | `LendingError` | `Library` のメソッド |
| 保存ファイルの内容の誤り | 知らない行、項目の数の違い、矛盾（存在しない利用者への貸出） | `StoreError { line, kind }` | `store::load` |
| 環境の問題 | ファイルが読めない・書けない | `std::io::Error` | ファイルの読み書き |
| コマンドの使い方の誤り | 引数が足りない、知らないオプション | `CliError::Usage` | `cli::parse_args` |
| プログラムのバグ | 確かめたはずの本が無い | （型にしない。`expect` で panic） | — |

### 層ごとのエラー型

```text
main.rs     終了コードを決める（Usage → 2、Lending → 1、それ以外 → 3）
  ▲
cli         CliError { Usage | Io{path} | Store{path} | Lending }   ← 下の層のエラーを包み、ファイル名を添える
  ▲
store       StoreError { line, kind }                               ← 何行目か。矛盾は LendingError を中に持つ
  ▲
library     LendingError                                            ← ルールの拒否。ファイルのことは知らない
  ▲
ids / date   InvalidId / ParseDateError
```

下の層のエラーは、上の層で**情報を足して**包みます。
`store` は「何行目か」を、`cli` は「どのファイルか」を足します。
下の層は、自分より上のことを知りません。`LendingError` は、ファイルという言葉を一度も使いません。

### `LendingError` を1つの enum にした理由

操作ごとに分ける案もありました。

| 案 | 良い点 | 困る点 |
| --- | --- | --- |
| 操作ごと（`BorrowError`、`ReturnError`） | `return_book` が「上限に達している」を返すことがない、と型で分かる | 型が増える。「存在しない本」が両方に重複する |
| 1つの `LendingError`（**選んだ**） | 型が1つ。呼ぶ側（CLI）の処理が1通り | どの操作がどの variant を返すかは、ドキュメントを読む必要がある |

判断の基準は、**呼ぶ側が variant ごとに違う対応をするか**です。
このツールの CLI は、どの `LendingError` でも「メッセージを表示して終了コード 1」で、対応は同じです。
それなら、分けても得がありません。
もしライブラリとして公開し、利用者が「上限なら別の本を勧める」のような対応をするなら、分ける価値が出てきます。

### 終了コードで、失敗の種類を区別する

| 終了コード | 意味 | 利用者（やスクリプト）がすること |
| --- | --- | --- |
| 0 | 成功 | — |
| 1 | ルールで断られた | 操作を見直す（別の本を選ぶ、先に返却する） |
| 2 | コマンドの使い方の誤り | 使い方を見て、打ち直す |
| 3 | ファイルの問題 | ファイルを確かめる（壊れていないか、権限はあるか） |

`anyhow` のような「エラーを1つの型にまとめる crate」を使うと、ここで種類を見分けにくくなります。
区別したい種類が少なく決まっているので、`CliError` の enum を自分で書きました。

### 「何も変えずに」を守る（R10）

`Library::borrow` は、**全てのルールを確かめ終わってから**、本の状態を書き換えます。

```text
利用者はいるか → 本はあるか → 貸出可か → 延滞はないか → 上限は → （ここで初めて書き換える）
```

途中で `?` や `return Err(…)` で抜けても、まだ何も変えていないので、データは元のままです。
CLI も、`execute` が `Err` を返したらファイルを書かずに終わります。

### panic してよい場所

| 場所 | 理由 |
| --- | --- |
| `borrow` の最後の `get_mut(book_id).expect("上で存在を確かめている")` | 同じ関数の中で存在を確かめた直後。ここで `None` になるなら、それはプログラムのバグ |
| `String` への `write!` の結果 | `String` への書き込みは失敗しない |

利用者の入力やファイルの中身が原因で panic することは、ありません。

## よくある失敗

| 失敗 | 何が困るか | 直し方 |
| --- | --- | --- |
| 全てを `String` のエラーにする | 呼ぶ側が種類を見分けられない。テストで「どの失敗か」を確かめられない | 対応が変わる種類ごとに、variant を分ける |
| 下の層のエラーが、上の層の言葉を使う | `LendingError` に「ファイルの何行目」が入ると、ルールのテストにファイルの概念が混ざる | 情報は、それを知っている層で足す |
| 途中まで書き換えてから失敗する | 「上限でした」と言われたのに、本の状態だけ貸出中になっている | 確かめる → 書き換える、の順番を守る |
| 入力の誤りで `unwrap` する | 利用者のタイプミスで panic し、原因も分からない | `unwrap` / `expect` は「絶対に起きない」と言える理由があるときだけ。理由をメッセージに書く |
