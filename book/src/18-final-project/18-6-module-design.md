# 18-6 Module Design: ファイルの分け方と、依存の向き

## この段階でやること

コードをどのファイル（モジュール）に分けるかと、**どのモジュールがどれを使ってよいか**（依存の向き）を決めます。
あわせて、ここまで後回しにしていた「外側」の形を決めます。

- コマンドライン: どんなコマンドと引数にするか
- 保存: どんな形式のファイルにするか

ドメイン（18-2〜18-5）を先に決めてから外側を決めるのは、**外側の都合でドメインが歪まないように**するためです。

## 入力と出力

| 受け取るもの | 書くもの |
| --- | --- |
| 18-3〜18-5 の型・エラーの設計 | モジュールの一覧と役割 / 依存の向きの図 / I/O（ファイル・時計・標準出力）を扱う場所 / コマンドの形 / 保存形式 |

## 考える問い

1. ドメイン（ルール）のモジュールは、ファイルやコマンドライン引数のことを**知らずに**済みますか？
2. 依存の向きを矢印で描いてください。**循環**（A が B を使い、B が A を使う）はありませんか？（Lesson 12-3）
3. I/O（ファイルを読む、時計を読む、画面に出す）は、何か所に散らばっていますか？ 1か所に集められますか？
4. `main.rs` には何が残りますか？（Lesson 12-2）
5. 保存形式は、人が読めるテキスト？ JSON？ バイナリ？ 何を基準に選びますか？
6. 保存形式を将来変えたとき、古いファイルをどう見分けますか？

### モジュールと役割

| モジュール | 役割 | I/O |
| --- | --- | --- |
| `ids` | `BookId` / `MemberId` | なし |
| `date` | `Date` | なし |
| `member` | `Member` | なし |
| `library` | `Library` と貸出・返却のルール、`LendingError` | なし |
| `store` | `Library` ⇔ テキストの変換、`StoreError` | **なし**（文字列を受け取り、文字列を返す） |
| `cli` | 引数の解釈（`parse_args`）、コマンドの実行（`execute`）、ファイルの読み書き（`run`） | `run` の中だけ |
| `main.rs` | 時計を読む、`run` を呼ぶ、表示する、終了コードを決める | 時計と標準出力 |

### 依存の向き

```text
main.rs ──▶ cli ──▶ store ──▶ library ──▶ member ──▶ ids
             │                   │
             └───────────────────┴────────▶ date
```

矢印は「使う」の向きです。逆向きの矢印はありません。

- `library` は `store` も `cli` も知りません。保存形式を JSON に変えても、コマンドを GUI に変えても、`library` は変わりません
- `store` は `library` を知っていますが、ファイルを開きません。ファイルを開くのは `cli::run` だけです

### I/O を端に寄せる

I/O を含まない関数は、引数を渡して戻り値を確かめるだけでテストできます。
例題では、I/O を次の2か所に集めました。

| I/O | 場所 | テストのしかた |
| --- | --- | --- |
| 時計を読む | `main.rs` の `system_today` | テストしない（数行だけ）。他は全て `today: Date` を引数で受け取る |
| ファイルを読み書き | `cli::run` の中の `load_file` / `save_file` | バイナリを実際に動かすテスト（一時ディレクトリを使う） |

それ以外（`parse_args`、`execute`、`store::save` / `load`、`Library` の全メソッド）は、**I/O なしで**テストできます。

### lib と bin を分ける

`src/lib.rs` にすべてのモジュールを置き、`src/main.rs` は薄くしました（Lesson 12-2）。
`tests/` の統合テストから `Library` や `cli::parse_args` を直接呼べるようにするためです。

`lib.rs` では、全てのモジュールを `pub mod` にしたうえで、よく使う型を `pub use` で直下に並べています。
P7 のように `mod` を非公開にしなかったのは、これが**他の人に配るライブラリではなく、アプリケーションの内部**だからです。
公開範囲を狭くする利点（あとで変えても利用者が壊れない）が、ここでは小さいと判断しました。

### コマンドの形

```text
lending [--data FILE] [--today YYYY-MM-DD] <command>

  add-book   <book-id> <title>
  add-member <member-id> <name>
  borrow     <member-id> <book-id>
  return     <book-id>
  loans      <member-id>
  overdue
  list
```

- `--today` を用意したのは、動作を確かめるときに日付を自由に決めたいため（要件の「タイムゾーンは範囲外」を補う）
- `return` は本の ID だけを受け取る。誰が借りているかは、本の状態から分かる（18-2 で決めた「覚える場所は1つ」）

### 保存形式

タブ区切りのテキストにしました。

```text
# lending v1
member	M001	山田 花子
book	B001	Rustの本	available
book	B002	型の本	loan	M001	2026-09-01	2026-09-15
```

| 候補 | 良い点 | 困る点 |
| --- | --- | --- |
| タブ区切りのテキスト（**選んだ**） | 人が読める。git で差分が読める。依存なし | エスケープ（書名にタブが入る場合）を自分で書く |
| JSON（`serde` + `serde_json`） | 形式の仕様が決まっている。入れ子も表せる | 依存が2つ増える。行番号つきのエラーを出すには工夫が要る |
| バイナリ | 小さく速い | 人が読めない。壊れたときに直せない |

- 1行目の `# lending v1` は、形式の**版**です。形式を変えるときは `v2` にし、古いファイルを見分けられるようにします
- 書名に含まれるタブや改行は、`\t` `\n` に置き換えて保存します。「書名にタブを使えない」という制限を、保存形式の都合でドメインに持ち込まないためです
- 書き込みは、一時ファイルに書いてから名前を付け替えます。途中で止まっても、元のファイルが半分だけ書かれた状態で残りません

### 読み込み時にルールを確かめ直さない

保存ファイルを読むとき、貸出の上限（R5）などのルールは確かめ直しません。
あとでルールが変わったとき（たとえば上限を 3 冊から 2 冊に減らしたとき）、**過去の正しい記録が読めなくなる**のを防ぐためです。
読み込みで確かめるのは、データとしての矛盾（ID の重複、存在しない利用者への貸出）だけです。
そのため、`Library` には `store` 専用の `pub(crate) fn restore_book` を用意しました。

## よくある失敗

| 失敗 | 何が困るか | 直し方 |
| --- | --- | --- |
| ドメインのメソッドの中でファイルを読み書きする | ルールのテストに、毎回ファイルが要る | ドメインは値を受け取り値を返すだけにし、I/O は外側で |
| ドメインの中で時計を読む | 「期限の翌日」のテストが書けない | 日付を引数で受け取る |
| `utils` / `common` という名前のモジュール | 何でも入り、全モジュールがそこに依存する | 役割の名前をつける（`date`、`ids`） |
| 保存形式に版を入れない | 形式を変えたとき、古いファイルを読んで壊れたデータになる | 先頭に版を書き、知らない版は読まずにエラー |
