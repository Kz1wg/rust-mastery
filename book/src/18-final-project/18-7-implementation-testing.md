# 18-7 Implementation & Testing: 要件ごとにテストを書きながら作る

## この段階でやること

ここで初めて、本格的にコードを書きます。
進め方の軸は、**要件（R1〜R10）を1つずつ、テストと一緒に実装する**ことです。

```text
要件を1つ選ぶ
  ↓
その要件を確かめるテストを書く（まだ失敗する）
  ↓
テストが通るように実装する
  ↓
cargo test / cargo clippy / cargo fmt
  ↓
次の要件へ
```

実装しているうちに、設計メモと違うことをしたくなる場面が必ず来ます。
そのときは、**先に設計メモを直してから**コードを直してください。
設計メモとコードがずれたままだと、18-8 で「なぜこうしたのか」を思い出せなくなります。

## 入力と出力

| 受け取るもの | 書くもの |
| --- | --- |
| 18-1〜18-6 の設計メモ | コード / 要件とテストの対応表 / 実装中に設計を変えた点の記録 |

## 考える問い

1. どの順番で作りますか？ **何にも依存しないもの**から作ると、すぐにテストできます
2. 各要件のテストに、**境目**（期限の当日と翌日、上限ちょうど）は入っていますか？
3. 「断られたら何も変わらない」（R10）は、どうやってテストしますか？
4. どのテストを、どこに置きますか？（モジュールの中の `#[cfg(test)]`？ `tests/` の統合テスト？ バイナリを動かすテスト？）
5. 自分で作った `Date` のような部品は、**どれくらい**テストすれば安心できますか？

## 作る順番の例

依存の向き（18-6）の**矢印の先から**作ります。そうすると、作ったものをすぐにテストできます。

| 順番 | 作るもの | この時点でテストできること |
| --- | --- | --- |
| 1 | `ids`、`date` | ID の規則、日付の変換・計算（うるう年、月末、年末） |
| 2 | `member`、`library` | R1〜R8、R10（ファイルも CLI も無しで） |
| 3 | `store` | R9 の変換部分（文字列だけで） |
| 4 | `cli`、`main.rs` | R9 のファイル部分、コマンドの形、終了コード |

2 が終わった時点で、**ルールは全て動いています**。
画面もファイルも無いのに、図書室として正しく動くことをテストで確かめられるのは、
ドメインを外側から切り離した（18-6）おかげです。

## テストの置き場所

| 置き場所 | 向いているもの | 例題での例 |
| --- | --- | --- |
| モジュールの中（`#[cfg(test)] mod tests`） | 非公開の関数や、部品の細かい動き | `date` の変換、`store` のエスケープ |
| `tests/*.rs`（統合テスト） | 要件。**公開された API だけ**を使って確かめる | `tests/scenarios.rs`（R1〜R8, R10）、`tests/store.rs`（R9） |
| バイナリを実際に動かすテスト | ファイルの保存、終了コード、表示 | `tests/cli.rs`（`env!("CARGO_BIN_EXE_lending")` でビルド済みのバイナリを起動） |

要件のテストを統合テストに置くと、**内部の作りを変えてもテストを直さずに済みます**（18-8 で効いてきます）。

## テストの名前で、要件と結びつける

```rust,ignore
#[test]
fn r6_member_with_overdue_book_cannot_borrow() {
    let mut lib = library();
    lib.borrow(&member("M1"), &book("B1"), d("2026-09-01")).unwrap(); // 期限 09-15

    // 期限当日はまだ延滞ではない
    assert!(lib.borrow(&member("M1"), &book("B2"), d("2026-09-15")).is_ok());

    // 翌日からは延滞
    assert_eq!(
        lib.borrow(&member("M1"), &book("B3"), d("2026-09-16")),
        Err(LendingError::HasOverdue { member: member("M1"), book: book("B1") })
    );

    // 延滞している本を返せば、また借りられる
    lib.return_book(&book("B1"), d("2026-09-16")).unwrap();
    assert!(lib.borrow(&member("M1"), &book("B3"), d("2026-09-16")).is_ok());
}
```

テスト名の先頭の `r6_` で、どの要件のテストかが分かります。
`cargo test r6` で、その要件のテストだけを走らせることもできます。

1つのテストの中に、18-1 で決めた**境目**（期限の当日・翌日）と、**回復**（返せばまた借りられる）が入っていることに注目してください。

## 「何も変わらない」をテストする

R10 の「断られたら何も変えない」は、次のように確かめられます。

```rust,ignore
let before = lib.clone();
assert!(lib.borrow(&member("X"), &book("B1"), today).is_err());
assert_eq!(lib, before); // 図書室全体が、呼ぶ前と同じ
```

`Library` に `Clone` と `PartialEq` を付けたのは、このテストのためでもあります（18-4）。

## 参考実装を見る

ここまで来たら、参考実装 [projects/final_lending](https://github.com/Kz1wg/rust-mastery/tree/main/projects/final_lending) を開いてかまいません。
なお、参考実装は **18-8 の変更（利用者の種別）を入れた後**の状態です。

```bash
cd projects
cargo test -p final_lending
```

参考実装と自分のコードを見比べるときは、**行ごとの違い**ではなく、**判断の違い**を探してください。

| 見比べる点 | 問い |
| --- | --- |
| 型 | 自分は `Option<Loan>` にしたが、参考実装は `enum` にした。自分の要件では、どちらが合っているか |
| エラー | 自分は操作ごとにエラー型を分けた。それで呼ぶ側のコードは、どう変わったか |
| テスト | 参考実装にあって、自分に無いテストは何か。それは、自分の要件でも必要か |

参考実装と違う判断をしていても、**理由を説明できれば**それで構いません。

## よくある失敗

| 失敗 | 何が困るか | 直し方 |
| --- | --- | --- |
| 全部書き終えてから、テストを書く | どこが間違っているか分からない。テストが「今の動き」をなぞるだけになる | 要件1つごとに、テスト → 実装 |
| テストが内部の作りに依存する | 18-8 で作りを変えるたびに、テストも直すことになる | 要件のテストは、公開された API だけで書く |
| 成功する場合だけテストする | 境目やエラーの扱いが、テストされないまま残る | 18-1 の「決めたこと」を、1つずつテストにする |
| 設計メモを直さずに、コードだけ変える | 設計メモが役に立たなくなる | 設計を変えたら、メモの該当箇所と「レビューの記録」を更新する |

## AI にレビューしてもらう

コードのレビューでは、**設計メモも一緒に渡す**のがコツです。
設計メモが無いと、AI は一般的な「良いコード」の基準でレビューするので、
あなたが意図して選んだ設計（trait を作らない、など）を「改善点」として指摘してきます。

````text
次は、Rust で作ったコマンドラインツールのコードと、その設計メモです。
設計メモに書いた方針を前提に、次の観点でレビューしてください。

1. 設計メモと、実装が食い違っている所
2. 要件（R1〜R10）のうち、テストで確かめられていないもの、境目のテストが無いもの
3. 失敗したときにデータが途中まで変わる可能性がある所
4. unwrap / expect で、実際には起こりうる失敗を panic にしている所

設計メモの方針そのものに反対する場合は、別の項目として、理由とともに書いてください。

---
（設計メモ）
（コード）
````
