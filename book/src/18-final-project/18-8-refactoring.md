# 18-8 Refactoring: 変更要求に、設計はどれくらい耐えられるか

## この段階でやること

作り終えたツールに、**変更の要求**が来ます。

> 「職員の先生たちから、3冊・2週間では足りないと言われました。
> 職員は **10 冊・30 日**まで借りられるようにしてください。一般の利用者は今までどおりです。」

この変更を入れながら、次の2つを確かめます。

- 変更は、コードの**どの範囲**に広がったか
- 変更の前に、**振る舞いを変えずに**構造を整えておけることはあったか

振る舞いを変えずに、コードの構造だけを変えることを**リファクタリング**と呼びます。
「機能を足す」と「構造を整える」を**別の手順に分ける**のが、この段階の一番のポイントです。

## 入力と出力

| 受け取るもの | 書くもの |
| --- | --- |
| 動いているコードとテスト、設計メモ、変更要求 | 更新した設計メモ / 変更の手順 / 変更が広がった範囲の記録 / 振り返り |

## 考える問い

1. 変更要求を、18-1 の要件の形に書き直してください。**どの要件が変わり**、どれが変わりませんか？
2. 「3冊」「14日」という数は、今のコードの**何か所**に書かれていますか？
3. 利用者ごとに違うルールを、どこに持たせますか？（利用者のフィールド？ 種別の `enum`？ 設定ファイル？）
4. 保存ファイルの形式は変わりますか？ **すでに保存されているファイル**はどうなりますか？
5. コマンドの形は変わりますか？ 今までのコマンドの使い方は、そのまま使えますか？
6. 既存のテストのうち、**直す必要があるもの**はどれですか？ 直さずに済むものはどれですか？

## 手順1: 振る舞いを変えずに、構造を整える

いきなり「職員」を足す前に、まず**今の振る舞いのまま**、変更しやすい形に整えます。

v1 のコードでは、ルールの数が `borrow` の中に直接書かれていました。

```rust,ignore
// v1
const MAX_LOANS: usize = 3;
const LOAN_DAYS: u32 = 14;

pub fn borrow(&mut self, member_id: &MemberId, book_id: &BookId, today: Date) -> Result<Date, LendingError> {
    // …
    if count >= MAX_LOANS { /* … */ }
    let due = today.add_days(LOAN_DAYS);
    // …
}
```

これを、「ルールの組」を返す関数に取り出します。**まだ全員が同じルール**です。

```rust,ignore
pub struct Policy {
    pub max_loans: usize,
    pub loan_days: u32,
}

fn policy_for(_member: &Member) -> Policy {
    Policy { max_loans: 3, loan_days: 14 }   // まだ全員同じ
}

pub fn borrow(&mut self, member_id: &MemberId, book_id: &BookId, today: Date) -> Result<Date, LendingError> {
    let member = /* … */;
    let policy = policy_for(member);
    // …
    if count >= policy.max_loans { /* … */ }
    let due = today.add_days(policy.loan_days);
    // …
}
```

振る舞いは変わっていないので、**既存のテストは1つも直さずに通るはず**です。
ここで `cargo test` が通れば、構造の変更で何も壊していないことが確かめられます。

> **なぜ分けるのか**
>
> 構造の変更と機能の追加を同時に行うと、テストが失敗したときに、
> どちらが原因か分からなくなります。
> 分けておけば、手順1で失敗したら「構造の変更で壊した」、手順2で失敗したら「新しい機能の問題」と、原因が絞れます。

## 手順2: 機能を足す

`policy_for` の中身を、利用者の種別で分けるように変えれば、変更の中心は終わりです。
ただし、**波及する場所**がいくつかあります。

<summary>例題の設計メモ（Refactoring）</summary>

### 要件の変更

| 番号 | 変更前 | 変更後 |
| --- | --- | --- |
| R2 | 利用者を ID と名前で登録できる | 利用者を ID と名前と**種別（一般 / 職員）**で登録できる |
| R3 | 返却期限は貸出日の 14 日後 | 返却期限は貸出日の、一般 14 日後 / 職員 30 日後 |
| R5 | 3 冊まで | 一般 3 冊まで / 職員 10 冊まで |
| R9 | （変更なし） | 加えて: 種別の無かった頃のファイルも読める。そのときは全員を一般とみなす |

R1・R4・R6・R7・R8・R10 は変わりません。

### 種別のルールを、どこに持たせるか

| 案 | 良い点 | 困る点 |
| --- | --- | --- |
| `Member` に `max_loans` と `loan_days` を持たせる | 1人ずつ違うルールにできる | 「職員のルールを 12 冊に変える」ときに、全職員のデータを書き換える必要がある |
| 設定ファイルで種別ごとの数を決める | コードを変えずにルールを変えられる | 設定ファイルの読み込み・検証・エラー処理が増える。今の要求には大きすぎる |
| `enum MemberKind` と、種別ごとのルールを返す `match`（**選んだ**） | ルールが1か所にまとまる。種別を足すと `match` がコンパイルエラーになり、ルールの決め忘れがない | ルールを変えるには、コードの変更とビルドが必要 |

```rust,ignore
pub enum MemberKind {
    General,
    Staff,
}

impl MemberKind {
    pub fn policy(self) -> Policy {
        match self {
            MemberKind::General => Policy { max_loans: 3, loan_days: 14 },
            MemberKind::Staff => Policy { max_loans: 10, loan_days: 30 },
        }
    }
}
```

「ルールの数を頻繁に変える」という要求が来たら、そのときに設定ファイルを検討します。

### 変更が広がった範囲

| ファイル | 変更 | 理由 |
| --- | --- | --- |
| `member.rs` | `MemberKind`・`Policy` を追加。`Member` に `kind` | 変更の中心 |
| `library.rs` | `add_member` に `kind` の引数。`borrow` が `member.kind.policy()` を使う。`LoanLimitReached` に `limit` を追加 | 上限が人によって違うので、エラーメッセージに「何冊が上限か」を入れる必要が出た |
| `store.rs` | 保存形式を **v2** に（member の行に種別）。**v1 のファイルも読める**ようにした | 既に保存されているファイルを、読めなくしないため |
| `cli.rs` | `add-member` に種別の引数 | 登録のときに種別を決める |
| テスト | R3・R5 のテストを種別ごとに書き直し。v1 のファイルを読むテストを追加 | 要件が変わったテストだけを直す |

**変わらなかったもの**: `ids.rs`、`date.rs`、`main.rs`、R1・R4・R6・R7・R8・R10 のテスト、エラーの層の構造。

変更は「ルールの中心（`member.rs`）」と「外との境目（`store.rs`・`cli.rs`）」に集まり、
日付や ID の部品、他の要件のテストには広がりませんでした。
18-6 で、ドメインと外側を分け、依存の向きを一方向にしておいた効果です。

### 保存形式の移行

```text
# lending v1                     # lending v2
member	M001	山田 花子    ──▶   member	M001	general	山田 花子
```

`store::load` は、1行目の版を見て読み方を変えます。

| 1行目 | member の行 | 種別 |
| --- | --- | --- |
| `# lending v1` | `member ID 名前`（3項目） | 全員 general とみなす |
| `# lending v2` | `member ID 種別 名前`（4項目） | 書かれたとおり |
| それ以外 | — | 読まずにエラー（`UnsupportedFormat`） |

保存するときは、常に v2 で書きます。v1 のファイルは、次に何かを変更したときに自然に v2 へ移ります。
18-6 で「1行目に版を書く」と決めておいたので、この移行が数行で書けました。
版が無かったら、「3項目の行は古い形式だろう」と**推測**するしかありませんでした。

### コマンドの互換性

`add-member M001 "山田 花子"`（v1 の形）は、v2 では**使い方の誤り**になります。

| 案 | 良い点 | 困る点 |
| --- | --- | --- |
| 種別を必須の引数にする（**選んだ**） | 登録のたびに種別を意識する。職員を一般で登録してしまう間違いが起きにくい | v1 の使い方がエラーになる |
| `--staff` のような省略できるオプションにする（省略したら一般） | v1 の使い方がそのまま動く | 付け忘れると、職員が一般として登録される。エラーにならないので気づきにくい |

このツールは係の人が手で打って使うもので、スクリプトから呼ばれていないので、必須にしました。
スクリプトから使われているツールなら、互換性を優先して省略できる形を選ぶ場面です（Lesson 16-2 と同じ考え方）。

### 振り返り

- 数を直接書いていた場所が `borrow` の中の2か所だけだったので、手順1は短く済んだ
- 保存形式に版を入れておいたことが、一番効いた
- `LoanLimitReached` に上限の数が無かったのは、v1 の見落とし。上限が固定なら不要な情報だったが、
  「エラーメッセージに、直すのに必要な情報を入れる」（18-5）の観点で、最初から入れておいてもよかった
- 要件のテストを公開 API だけで書いていたので、内部の変更（`Policy` の取り出し）でテストを直す必要がなかった

## よくある失敗

| 失敗 | 何が困るか | 直し方 |
| --- | --- | --- |
| 構造の変更と機能の追加を同時にする | テストが失敗したとき、原因が絞れない | 手順1（振る舞いを変えない）→ テスト → 手順2（機能を足す） |
| 保存形式を変えて、古いファイルを読めなくする | 利用者のデータが、更新した瞬間に使えなくなる | 版を見て読み分ける。移行の方法を決めてから形式を変える |
| 設計メモを更新しない | 次の変更のとき、どの判断がまだ有効か分からない | 要件・型・保存形式のメモを、変更に合わせて直す |
| 「ついでに」直す | 変更の範囲が広がり、レビューもテストも大変になる | 気づいた改善は、メモに書いて別の変更にする |

## AI にレビューしてもらう

````text
次は、Rust で作ったツールに入れた変更です。変更要求、更新した設計メモ、変更の差分を渡します。
次の観点でレビューしてください。

1. 変更要求のうち、実装されていないもの、テストされていないものはありますか
2. 変更前に保存されたデータや、変更前の使い方で、壊れるものはありますか
3. 今回の変更に含める必要のない変更（ついでの修正）が混ざっていませんか
4. 次に似た変更要求（たとえば、種別がもう1つ増える）が来たとき、どこを変えることになりますか

---
（変更要求）
（設計メモ）
（差分: git diff の出力など）
````

4つめの問いは、今回の設計が**次の変更**にも耐えられるかを確かめるためのものです。
例題なら、「種別がもう1つ増える」ときに変える場所は、`MemberKind` と、その `policy`・`Display`・`FromStr` だけのはずです。
`policy` と `Display` は `MemberKind` の `match` なので、足し忘れはコンパイラが教えてくれます。
一方、`FromStr` は**文字列**の `match`（`"general" => …`、それ以外 → エラー）なので、足し忘れてもコンパイルが通ります。
こういう「コンパイラが見てくれない場所」こそ、テストで確かめます（`Display` で書いて `FromStr` で読み戻すテストを、全ての種別について書くなど）。

## チェックリスト

- [ ] 変更要求を、要件の差分として書いた（変わる要件と、変わらない要件）
- [ ] 振る舞いを変えない手順と、機能を足す手順を分け、それぞれでテストを通した
- [ ] 保存されたデータと、今までの使い方への影響を確かめ、対応を決めた
- [ ] 変更が広がったファイルと、変わらなかったファイルを記録した
- [ ] 振り返りで「最初の設計で効いたこと」と「最初にやっておけばよかったこと」を書いた
- [ ] AI のレビューを受け、採用・不採用とその理由を記録した
