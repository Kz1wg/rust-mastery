# 18 Final Project

## この章でやること

最後の章では、**小さなアプリケーションを、何もないところから設計して作ります**。

これまでの演習やプロジェクトでは、型や関数のシグネチャ（名前・引数・戻り値の形）を教材の側で用意していました。
学習者の仕事は、その中身を書くことでした。
この章では、**シグネチャを決めるところから**自分でやります。

実務で難しいのは、実はこちらです。
「`borrow` 関数は `Result<Date, LendingError>` を返す」と決まっていれば、中身を書くのはそれほど難しくありません。
難しいのは、「そもそも `borrow` という関数が必要か」「何を返すべきか」「失敗にはどんな種類があるか」を決めることです。

## 設計の流れ

この章は、次の順番で進みます。1つの段階が、1つのページです。

```text
18-1 Requirements     何を作るか。何を作らないか
  ↓
18-2 Domain Model     登場するものと、そのあいだの関係・ルール
  ↓
18-3 Type Design      ルールを型で表す
  ↓
18-4 Trait Design     trait が必要な場所はあるか
  ↓
18-5 Error Design     失敗の種類と、誰がそれを処理するか
  ↓
18-6 Module Design    ファイルの分け方と、依存の向き
  ↓
18-7 Implementation & Testing   要件ごとのテストを書きながら実装する
  ↓
18-8 Refactoring      変更要求が来たとき、設計はどれくらい耐えられるか
```

各段階で、**1ページの設計メモ**を書きます。
コードを書くのは 18-7 からです。それまでは、文章と表と、型のスケッチ（中身のない定義）だけを書きます。

> **なぜ、いきなりコードを書かないのか**
>
> コードを書き始めると、目の前のコンパイルエラーを直すことに意識が向き、
> 「この設計で良いのか」を考える余裕がなくなります。
> 先に言葉で決めておくと、迷ったときに戻る場所ができます。
> また、設計メモは AI にレビューしてもらうときの材料にもなります（後述）。
>
> ただし、設計メモを完璧にしてからコードを書く必要はありません。
> 18-7 で実装しながら「設計が間違っていた」と気づいたら、前の段階のメモに戻って直してください。
> **その行き来こそが、設計の練習です。**

## 2つの進め方

| 進め方 | 向いている人 | やること |
| --- | --- | --- |
| **A. 例題で進む** | 題材を考える時間を設計に使いたい人 | この章の例題「図書室の貸出管理」を、自分で設計して作る。各ページの「例題の設計メモ」は、**自分で書いてから**開く |
| **B. 自分の題材で進む** | 作りたいものがある人 | 自分で題材を決め、同じ段階を踏んで作る。例題の設計メモは、書き方の参考として読む |

B を選ぶ場合の題材の目安です。

| 良い題材の条件 | 例 |
| --- | --- |
| **ルール**がある（「〜のときは〜できない」） | 家計簿（予算を超えたら警告）、在庫管理（在庫が無いと出荷できない）、会議室の予約（時間が重なると予約できない） |
| **状態が変わる**ものがある | 注文（受付 → 発送 → 完了 / キャンセル）、タスク（未着手 → 作業中 → 完了） |
| **保存**が必要（次に起動したときも覚えている） | どれもファイルに保存する |
| 1〜2週間で作れる大きさ | 本体のコードで 500〜1500 行くらい |

避けたほうがよい題材は、「画面（GUI）が中心のもの」と「外部サービスの API に頼るもの」です。
設計の練習より、ライブラリの使い方を調べることに時間を取られてしまいます。

## 例題: 図書室の貸出管理

小さな図書室の、本の貸し出しと返却を管理するコマンドラインツールです。

```text
$ lending add-book B001 "Rustの本"
本 B001「Rustの本」を登録しました
$ lending add-member M001 general "山田 花子"
利用者 M001（山田 花子, general）を登録しました
$ lending --today 2026-09-01 borrow M001 B001
本 B001 を M001 に貸し出しました。返却期限は 2026-09-15 です
$ lending --today 2026-09-20 overdue
B001	Rustの本	M001	5日
```

図書室は、誰でも仕組みを想像できるうえに、「貸出中の本は借りられない」「延滞していると借りられない」といった
**ルール**が自然に出てきます。ルールがあると、型やエラーの設計に考えどころが生まれます。

参考実装は、[リポジトリ](https://github.com/Kz1wg/rust-mastery)の `projects/final_lending/` にあります（テストを含めて約 1800 行。そのうち `tests/` が約 500 行）。
**18-7 まで進むまで、参考実装のコードは開かないでください。** 先に見ると、それが「正解」に見えてしまい、自分で考える機会がなくなります。
参考実装は、数ある良い設計の**1つ**にすぎません。

```bash
cd projects
cargo test -p final_lending                     # 参考実装のテスト
cargo run -p final_lending -- --data /tmp/lib.tsv list   # 動かしてみる
```

## 設計メモの置き場所

自分の設計メモは、テンプレート [docs/final-project-template.md](https://github.com/Kz1wg/rust-mastery/blob/main/docs/final-project-template.md) をコピーして書き始めてください。
リポジトリを手元に用意していれば、次のコマンドでコピーできます（用意のしかたは [Lesson 00-2](../00-introduction/00-2-cargo-test.md)）。

```bash
cp docs/final-project-template.md my-design.md
```

テンプレートには、8つの段階それぞれの見出しと、書くべき項目が入っています。
A・B どちらの進め方でも同じテンプレートを使います。

## AI にレビューしてもらう

各段階の最後に、設計メモを AI に見せてレビューしてもらいます。
ここで大切なのは、**AI の指摘をそのまま受け入れない**ことです。

```text
設計メモを書く
  ↓
AI にレビューしてもらう（各ページにプロンプトの例があります）
  ↓
指摘を1つずつ読み、「採用する / 採用しない」を決める
  ↓
決めた理由を、設計メモの「レビューの記録」に書く
```

AI は、よく見かける設計を勧める傾向があります。
「trait を作って抽象化しましょう」「エラーは anyhow を使いましょう」といった指摘は、
一般論としては正しくても、あなたの題材には合わないことがあります。
**採用しない理由を説明できること**は、採用することと同じくらい大切です。

## 評価のしかた

この章には、`cargo test` で判定できる「正解」がありません。
かわりに、次の3つで自分の成果を確かめます。

| 何で確かめるか | 確かめること |
| --- | --- |
| **自分で書いたテスト** | 18-1 で決めた要件のそれぞれに、それを確かめるテストがあるか（18-7） |
| **各ページのチェックリスト** | その段階で考えるべきことを、考えたか |
| **レビューの記録** | AI（や人）の指摘に対して、理由をつけて判断したか |

最後に、18-8 の変更要求に対応したとき、**変更がどれくらいの範囲に広がったか**を記録してください。
変更が数か所で済んだなら、それは設計がうまくいった証拠です。
広い範囲に広がったなら、どこで設計を変えればよかったかを考えることが、この章の最後の学びになります。
