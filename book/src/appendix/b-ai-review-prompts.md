# B. AIレビュー用プロンプト集

この教材は、AI を使うことを禁止していません。
むしろ、次の流れで AI を**練習相手**として使うことをすすめています。

```text
AI にコードを書かせる
  ↓
自分でコードを読む
  ↓
問題点を見つける（AI にもレビューさせる）
  ↓
設計を、自分の言葉で説明する
  ↓
自分で直す
  ↓
cargo test
```

この付録は、その流れで使うプロンプトの例を集めたものです。
そのままコピーして、`（…）` の部分を書き換えて使ってください。

## プロンプトを書くときの5つのコツ

| コツ | 理由 |
| --- | --- |
| **前提を渡す**（要件、設計メモ、守りたい方針） | 前提が無いと、AI は一般的な「良いコード」の基準で答える。あなたが意図して選んだこと（trait を作らない、など）を「改善点」として指摘してくる |
| **観点を指定する** | 「レビューして」だけだと、書式や命名の指摘ばかりになりがち |
| **範囲を広げさせない** | 「〜も追加すると便利です」という提案は、レビューではなく機能追加。明示的に止める |
| **具体的な場面を求める** | 「抽象化すると柔軟になります」は検証できない。「どんな入力で、何が困るか」なら確かめられる |
| **根拠を求める** | 「この変更で、どのルールが守られるようになるか」を書かせると、中身のない提案を見分けられる |

## AI の答えを受け取ったら

AI の答えは、**仮説**として扱います。

- [ ] コードは、実際にコンパイルして、テストを走らせたか
- [ ] 指摘は、今の要件の範囲の話か。範囲を広げる提案が混ざっていないか
- [ ] 「一般的に良い」ではなく、このコードで**具体的に**何が困るのかが書かれているか
- [ ] 存在しない API や、古いバージョンの情報が混ざっていないか（とくに crate の使い方）
- [ ] `clone()`・`unwrap()`・`'static`・`unsafe` で、エラーを**黙らせる**直し方になっていないか
- [ ] 採用する / しないを決め、その**理由**を書いたか

最後の項目がいちばん大切です。
「採用しない理由を説明できる」ことは、「採用する」ことと同じくらい、設計の力を表します。

## 1. コードを書かせる

AI に書かせるときは、**制約**をはっきり書きます。
制約が無いと、AI は `unwrap()` や `clone()` の多い「動くコード」を返しがちです。

````text
次の関数を Rust で実装してください。

- シグネチャは変えないでください:
  （例: pub fn average(input: &str) -> Result<f64, AverageError>）
- 依存 crate は使わないでください（標準ライブラリのみ）
- unwrap / expect / panic! は使わないでください
- 不要な clone や、不要な String の確保をしないでください
- 実装の後に、あなたが判断に迷った点と、その判断の理由を箇条書きで書いてください

仕様:
（入力と出力、境目の扱い、エラーの扱い）
````

「判断に迷った点」を書かせると、仕様のあいまいな所が見つかります。

### 練習: 書かせたコードの問題を3つ探す

書かせたコードを、**AI に見せる前に**自分で読みます。

````text
（自分へのメモ）
1. このコードが panic する入力はあるか
2. 呼ぶ人から見て、シグネチャは何を約束しているか。実装はその約束を守っているか
3. 所有権: 借用で済む所で、所有権を要求していないか。不要なコピーはないか
4. エラー: 失敗の種類を、呼ぶ人が区別できるか
5. 型: ありえない状態を表現できてしまう型はないか
````

3つ見つけてから、次の「2. 設計レビュー」で AI にもレビューさせ、自分の発見と比べてください。

## 2. 設計レビュー（全般）

````text
次の Rust のコードをレビューしてください。前提となる要件と方針も添えます。

次の観点で、問題を重要な順に最大5つ挙げてください。
それぞれ「どんな入力・使い方で、何が困るか」を具体的に書いてください。

1. 正しさ（panic する入力、間違った結果を返す入力）
2. 型の設計（ありえない状態を表現できないか）
3. 所有権（不要な所有権の要求、不要なコピー）
4. エラー処理（失敗を呼ぶ人が区別・処理できるか）
5. API（呼ぶ人が間違った使い方をしにくいか）

書式や命名だけの指摘は不要です。新しい機能の提案もしないでください。

---
要件と方針:
（…）

コード:
（…）
````

## 3. 代替案を出させる（複数の実装を比べる）

1つの答えではなく、**比べる材料**を出させます（本文の Lesson 01-4 の形）。

````text
次の関数について、シグネチャの異なる実装を3つ示してください。
（例: 引数を Vec<String> で受け取る / &[String] で受け取る / impl IntoIterator で受け取る）

そのうえで、3つを次の観点で表にして比べてください。
どれが正解かは書かず、それぞれがどんな場面に向いているかを書いてください。

- 所有権（呼ぶ人は、呼んだ後も値を使えるか）
- メモリの確保（どこで、何回確保するか）
- API の柔軟さ（どんな型の値を渡せるか）
- 読みやすさ
- 性能
- 抽象化の度合い

関数の仕様:
（…）
````

「どれが正解かは書かず」がポイントです。書かせると、それ以外の案の良い点が説明されなくなります。

## 4. 過剰な抽象化を見つける

AI が書くコードは、trait や generic が多くなりがちです（本文 Lesson 04-5、ex017）。

````text
次の Rust のコードに、必要以上の抽象化がないか確かめてください。

次のそれぞれについて、「今あるコードの中で、実際に2つ以上の実装・型で使われているか」を確かめ、
使われていないものを挙げてください。

- 自分で定義した trait
- generic な型引数
- Box<dyn Trait>
- ビルダーやファクトリなどの間接的な作り方

それぞれについて、抽象化をやめた場合のコードを示し、
やめることで失うもの（あれば）を書いてください。

---
（コード）
````

「今あるコードの中で」と限定するのが大切です。
「将来、別の実装が必要になるかもしれない」は、抽象化を残す理由として弱いからです。

## 5. 型の設計をレビューする

````text
次の Rust の型定義について、「作れてしまうが、ありえない状態」を探してください。

例: 「貸出中なのに、借りた人がいない」「管理者ではないのに、管理者の権限を持つ」

見つけたそれぞれについて、
1. その状態を作るコード
2. その状態が作られると、どこで何が困るか
3. 型を変えてその状態を作れなくする案（enum、newtype、フィールドの非公開など）
を書いてください。
型で表すと複雑になりすぎる場合は、関数で確かめる案も示してください。

---
（型定義と、主な関数のシグネチャ）
````

## 6. エラーの設計をレビューする

````text
次の Rust のコードのエラー処理をレビューしてください。これは（ライブラリ / アプリケーション）です。

1. unwrap / expect / panic! のうち、実際に起こりうる失敗を panic にしているもの
2. 呼ぶ人が区別したいはずなのに、同じ種類のエラーにまとめられているもの
3. エラーメッセージを見ても、利用者がどこを直せばよいか分からないもの
4. 失敗したときに、データが途中まで変わった状態で残る可能性がある所

エラー処理の crate（anyhow / thiserror など）を勧める場合は、
今のコードと比べて何が具体的に良くなるかを書いてください。

---
（コード）
````

## 7. 所有権とライフタイムをレビューする

````text
次の Rust のコードについて、所有権とライフタイムの観点でレビューしてください。

1. clone() / to_string() / to_owned() のうち、借用で済むもの
2. 引数で所有権（T）を受け取っているが、借用（&T）で足りるもの。逆に、借用で受け取って中で複製しているもの
3. 'static を付けているが、本当は必要ないもの
4. 参照を持つ struct のうち、所有する値にしたほうが単純になるもの

それぞれ、変更後のコードと、変更で呼ぶ人のコードがどう変わるかを書いてください。

---
（コード）
````

## 8. 並行処理・async をレビューする

````text
次の Rust のコードを、並行処理の観点でレビューしてください。

1. ロック（Mutex / RwLock）を持ったまま、時間のかかる処理や .await をしている所
2. デッドロックの可能性（ロックを取る順番が場所によって違う、など）
3. async の中で、スレッドを止めてしまう処理（std::thread::sleep、同期の I/O、重い計算）
4. Arc<Mutex<T>> を使っているが、チャネル（mpsc）や AtomicXxx のほうが単純になる所
5. タスクやスレッドが panic したときに、全体がどうなるか

コンパイラが防いでくれる問題（データ競合）ではなく、コンパイラが防がない問題を中心に見てください。

---
（コード）
````

最後の一文は、Chapter 10 の主題「データ競合が無いことと、正しく動くことは別」に対応しています。

## 9. unsafe をレビューする

````text
次の Rust のコードの unsafe ブロックを、1つずつレビューしてください。

それぞれの unsafe ブロックについて:
1. その操作が要求している条件（ポインタが有効、長さが正しい、境界の内側、など）を列挙してください
2. それぞれの条件が、このコードのどこで保証されているかを示してください。保証されていない条件があれば、
   その条件を破る safe なコードの例を示してください
3. // SAFETY: コメントが、1 と 2 を正しく説明しているか確かめてください

unsafe を使わずに書ける場合は、その書き方も示してください。

---
（コード）
````

2 の「条件を破る safe なコードの例」が書けてしまうなら、それは safe abstraction が壊れている（Lesson 15-2）ということです。

## 10. 公開 API をレビューする

````text
次は、他の人に使ってもらう Rust のライブラリの公開 API です（中身は省略しています）。
初めてこのライブラリを使う人の立場でレビューしてください。

1. 呼び出しのコードを読んだだけで、何をしているか分かりにくい所（bool の引数が並ぶ、など）
2. 間違った使い方をしても、コンパイルが通ってしまう所
3. 次のバージョンで変更すると、利用者のコードが壊れる可能性が高い所
   （pub なフィールド、網羅的な match を許す enum、既定の実装が無い trait のメソッド など）
4. 実装した方がよい標準の trait（Debug、Clone、Display、Error、Send / Sync であることの保証など）

---
（pub な型・関数・trait のシグネチャとドキュメントコメント）
````

## 11. テストをレビューする

````text
次は、Rust のコードとそのテストです。要件も添えます。

1. 要件のうち、テストで確かめられていないもの
2. 境目（0 件、1 件、ちょうど上限、期限の当日と翌日など）のテストが無いもの
3. 失敗する場合（エラーを返す場合）のテストが無いもの
4. 実装の内部に依存していて、内部を変えると壊れるテスト
5. 実装をなぞっているだけで、実装が間違っていても通ってしまうテスト

足りないテストは、テストのコードとして示してください。

---
要件:（…）
コード:（…）
テスト:（…）
````

## 12. コンパイルエラーを説明させる

エラーを「直させる」のではなく、「説明させる」ために使います（Appendix A の「5つの問い」）。

````text
次の Rust のコードは、下のエラーでコンパイルできません。
直したコードは、まだ示さないでください。かわりに、次の順番で説明してください。

1. 何が起きているか（何を借りて、何をしようとしたか）
2. なぜそれが許されないのか
3. コンパイラは、何を保証しようとしているのか
4. 直し方の候補を2つ以上
5. それぞれの直し方が、設計として望ましいかどうかと、その理由

---
コード:（…）
エラー:（…）
````

「直したコードは、まだ示さないで」と書いておくと、答えを先に見てしまうのを防げます。
自分で直してから、もう一度「直し方を示して」と頼んで、比べてください。

## 13. 自分の説明を確かめてもらう

各 Lesson の Review には、「〜を説明できる」という項目があります。
自分の説明を AI に見せて、**誤りや抜け**を指摘してもらいます。

````text
次は、Rust の（例: Send と Sync の違い）について、私が自分の言葉で書いた説明です。
正しいかどうかを確かめてください。

1. 事実として誤っている所
2. 重要なのに抜けている点
3. 正しいが、誤解を招きやすい言い方

説明を書き直すのではなく、指摘だけをしてください。

---
（自分の説明）
````

「書き直すのではなく、指摘だけ」と頼むのは、書き直された説明を読んでも、自分の理解にはならないからです。
